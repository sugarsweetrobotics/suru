# 今後の候補: スレッド

計画は7段階です。段階1(runtime の下ごしらえ)、段階2(並行開始する・合流する・並行実行する・並列写像する・コア数取得する)、段階3(通路)、段階4(ロック・枠・箱)、段階5(HTTP を接続ごとにスレッドで答える)、段階6(本当の並列: 安全点で止める GC、スレッドごとの確保、箱更新は比較交換)は済みました。

- GC の印付けと片付けを複数のスレッドで行うのは、今は見送る。たくさん確保する並列の計算(8 個の仕事でそれぞれ 30 万個の文字列を作る、200 万個の文字列を持ったまま同じことをする)で測ると、GC は全体の 3〜5%(3 回で 0.01〜0.03 秒)でした。並列で約 2.5 倍にとどまっていたのは、GC が少ない分だけ新しいブロックを多く使い、ページの割り当て(sys の時間)とキャッシュの外れが増えるためでした(2MB の塊と大きなページで縮めました。README「速さの改善」)。生きている値がもっと大きいプログラムで GC が目立つようになったら考える
- 複数の通路を同時に待つ(select)、時間切れつきの受信(「ないかもしれない値」の型ができてから)
- 読み書きロック(共有メモリなど外のものを読むスレッドが多いとき。読取実行する・書込実行する)。する の値と箱は読むのにロックが要らないので後回し
